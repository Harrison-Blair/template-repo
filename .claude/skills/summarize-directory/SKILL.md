# summarize-directory

Given a directory, produce two artifacts inside it:

- **INDEX.md** — a per-file directory: one section per top-level markdown file, each with an abstract (2–3 paragraphs) of what's inside that file plus a short bulleted list of the load-bearing claims, decisions, or discoveries it contains. The audience is a future agent that needs enough detail per file to decide whether to open it; humans read this only sparingly. The TOC link at the top of each section makes the file navigable without expanding every section.
- **SUMMARY.md** — a *directory-level* digest: an abstract (2–4 paragraphs) of what the directory collectively contains and how the pieces relate, followed by a bulleted list of cross-cutting decisions, opinions, and discoveries with file attribution. SUMMARY.md is *not* a per-file rollup — that's INDEX.md's job. Also echoed back in the chat response.

The skill recurses **one level only**. Re-run it inside each subdirectory you want summarized at depth — that keeps each invocation cheap and the resulting files focused on what's local.

## Inputs

- `<path>` — required. Absolute or relative; relative paths resolve against the user's current working directory. If the path is missing, ask for it before doing anything else. If the path doesn't exist or isn't a directory, say so plainly and stop.

## Workflow

### 1. Scan

Run the bundled scanner from the repo root (or wherever the skill was dropped):

```bash
bash .claude/skills/summarize-directory/scripts/scan.sh <path>
```

The output has six labelled sections:

- `[target]` — absolute path of the directory (resolves the relative input).
- `[existing]` — which of `INDEX.md` / `SUMMARY.md` / `README.md` already live at the target.
- `[top]` — top-level `*.md` files, with the three special filenames above and dotfiles excluded.
- `[sub]` — `*.md` files exactly one level deep, formatted as `subdir/file.md`.
- `[subdirs]` — immediate subdirectories that contain at least one `*.md`.
- `[skipped-dirs]` — immediate subdirectories ignored by the skip list (`node_modules`, `.git`, `.venv`, build/cache outputs, dotdirs).

If both `[top]` and `[sub]` are empty, tell the user the directory has no markdown to summarize and exit without writing anything.

### 2. Read the source files

- Read **every** file under `[top]` in full. INDEX.md gives each of them a per-file section with a 2–3-paragraph abstract and a bullet list of its key claims, so you need the actual content — filename + first heading is not enough. The abstract should pull out concrete things: named mechanisms, numbers, the alternative the author rejected and why. The bullets must be specific enough that a reader could decide *not* to open the file based on them; if a bullet would fit any file in any project, drop it.
- For files under `[sub]`, prefer reading the first heading + opening paragraph (skim, not full read) unless the file is short. The subdirectory section in INDEX.md is meant to be a pointer, not a full mirror — that's what running the skill again inside the subdirectory will produce.
- If a subdirectory has its own `INDEX.md`, you can lean on it: link to it instead of re-listing every file under that subdir.

### 3. Draft INDEX.md and SUMMARY.md *first*, then read existing files

This ordering matters. Reading the existing INDEX/SUMMARY/README *before* drafting tends to anchor your output on whatever the previous run wrote — which may be stale or wrong. Draft fresh from the source files first, then bring in the existing files as a *check*.

#### INDEX.md format

```markdown
# Index — <directory name>

_Generated by `/summarize-directory`. Optimized for AI traversal — re-run after meaningful changes._

## Contents

- [filename.md](#filenamemd) — one-line orientation (what the file is about, not its title rephrased).
- [other.md](#othermd) — …

---

## [filename.md](./filename.md)

<2–3-paragraph abstract of what's inside this file. Concrete: name the mechanisms, the constraints, and the shape of the content. The reader should be able to tell whether opening the file is worth it from this section alone.>

**Key claims:**

- <a load-bearing decision, opinion, or discovery from this file. Specific — numbers, named alternatives, the reason a trade-off broke the way it did.>
- …

---

## [other.md](./other.md)

…

---

## Subdirectories

- **subdir/** — one-line description of the subdirectory's collective purpose.
  - [subdir/file.md](./subdir/file.md) — brief one-liner.
  - …
```

Notes on the format:

- The top **Contents** section is a flat TOC of in-page anchors (`#filenamemd` style — GitHub-style auto-anchors, lowercased, dots and special chars stripped). It exists so a reader can jump without scrolling. Keep these one-liners terse.
- Each top-level file gets its own `## [filename.md](./filename.md)` section with the file *also* linked relative-path so the heading is clickable both ways. Below the heading: a 2–3-paragraph abstract, then a `**Key claims:**` bullet list. Bullets are specific and load-bearing — if a bullet could be true of any file in any project, drop it.
- For subdirectories, keep the section *light*. The skill is designed to be re-run inside the subdir; this index isn't trying to replace that. One line per subdir, with nested bullets only when the subdir has no `INDEX.md` of its own. If the subdir does have its own `INDEX.md`, replace the nested list with `- **subdir/** — see [subdir/INDEX.md](./subdir/INDEX.md).`.
- Skip the **Subdirectories** section entirely if no subdirectory has any markdown.
- Use relative links starting with `./` for file targets and `#anchor` for in-page targets so the index is portable when the directory is moved.

#### SUMMARY.md format

```markdown
# Summary — <directory name>

<abstract: 2–4 paragraphs covering what this directory is, the shape of its contents, and how the pieces relate to each other>

## Key decisions, opinions, and discoveries

- <concrete claim, decision, or opinion surfaced in the files; mention the source file when it makes the bullet more useful>
- …
```

Notes on the format:

- The abstract is prose, not a bulleted summary. It should help a reader who's never seen this directory understand the *shape* of what's here in under a minute.
- Bullets should be **specific and load-bearing**. "The files contain documentation about X" is filler — drop it. A claim is worth a bullet when it could change a future decision: a chosen design, a rejected alternative, a constraint, an empirical finding, a stated opinion.
- If the source files genuinely contain no decisions or opinions (e.g. a folder of pure reference material), that's fine — replace the bullet section with a single italic line saying so, rather than padding.

### 4. Reconcile with existing INDEX / SUMMARY / README

If `[existing]` named any of the three files, read them now and look for **insights present in the existing file but absent from your fresh draft** — historical context, decisions that current files leave implicit, motivations behind a structure that the source files don't restate. Pull those forward into the new draft.

What to drop:

- Claims contradicted by the current source files. The current state of the files is the source of truth.
- Filenames or links that no longer exist.
- Bullet points whose source file has been deleted or substantially rewritten.

What to keep:

- Domain context the source files assume but never explain.
- Opinions or decisions the previous summary captured that are still consistent with the current files.
- A `LOAD-BEARING-MARKER:` style anchor that the user has placed deliberately (treat any sentence the user explicitly tagged as load-bearing as something to preserve unless it's clearly contradicted).

This is judgment, not a mechanical merge. The fresh draft is the spine; the existing file is a source of supplementary context.

### 5. Write and echo

- Write `INDEX.md` and `SUMMARY.md` into the target directory. Overwrite if they already exist.
- Echo the **full SUMMARY.md content** back in the chat response, in a fenced markdown block so the user can read it without opening the file.
- Don't write anything else. The skill's blast radius is exactly two files at the target.

## Guardrails

- Only `INDEX.md` and `SUMMARY.md` at the target directory may be created or modified. Don't touch source markdown, don't touch files outside the target.
- If `<path>` is not a directory, exit with a clear error message — don't try to interpret a file path as a directory.
- If both `[top]` and `[sub]` are empty after the scan, tell the user there's nothing to summarize and exit. Don't write empty INDEX/SUMMARY files.
- Don't recurse below one level. Tell the user to re-run the skill inside the subdirectory if they want depth.
- Don't dump full file contents into the chat response. Echo SUMMARY.md only.

## Cross-platform notes

The scanner uses POSIX bash plus `mktemp`, `sort`, and standard test operators — the same toolchain other skills in this repo use (`update-readme`, `summarize-pr`). It runs unchanged on Linux, macOS, and Git Bash for Windows. Relative paths are resolved via `cd && pwd` inside the script, so callers don't have to pre-resolve.

## Drag-and-drop into another repo

Copy `.claude/skills/summarize-directory/` into the target repo's `.claude/skills/`. No other setup. The skill is self-contained — no shared scripts, no shared config.
